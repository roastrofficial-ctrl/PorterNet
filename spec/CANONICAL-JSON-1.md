# PORTER-CANONICAL-JSON/1

Status: normative Generation Zero amendment, 2026-09-29.

## Authority and decision

The PORTER Introduction and conformance documents require the canonical Package
digest but leave numeric formatting, Unicode ordering, escaping and input
validation unspecified. D-001 is a SPECIFICATION AMBIGUITY. Neither Python's
`json.dumps` nor Rust's `serde_json` defaults define the protocol.

This binding adopts [RFC 8785 JCS](https://www.rfc-editor.org/rfc/rfc8785), sections
3.1–3.2, as the canonical serialization of PORTER JSON values. The
[fixed vectors](vectors/canonical-json-1.json) are normative examples, not a
replacement for those rules. Expected bytes and hashes are stored, never
regenerated by either implementation during conformance checks.

## Input and numeric model

Input is one complete UTF-8 JSON text. A BOM, invalid UTF-8, trailing data,
duplicate decoded object names (even differently escaped), invalid JSON syntax,
lone surrogate escapes, NaN, Infinity and numeric overflow MUST be rejected.
A surrogate pair represents its single Unicode scalar. Validation must precede
lossy construction of a mapping; a last-key-wins parser is not conforming.

Every JSON number denotes the correctly rounded IEEE 754 binary64 value of its
decimal token, using round-to-nearest, ties-to-even. Programmatically supplied
integers likewise enter that numeric model. Overflow to infinity is rejected;
underflow rounds to signed zero. Negative zero serializes as `0`. Fractions,
exponent forms and integer forms representing the same binary64 value have the
same canonical bytes. A boolean is not a number.

This is an explicit representational decision: `9007199254740993` rounds to
`9007199254740992`. PORTER does not promise arbitrary-precision decimal or integer
identity in a JSON number. An application needing that precision must encode
its value as a string. No schema-driven coercion of a string into a number is
permitted. This choice was not earned by the old implementations; it is the
smallest adoption of an established complete numeric serialization rule.

## Output

Output is UTF-8 without BOM, trailing newline or inter-token whitespace. Object
names are recursively sorted by unsigned UTF-16 code units, not UTF-8 bytes or
Unicode scalar order. Array order is unchanged. Strings are not normalized:
composed and decomposed Unicode remain different. Control characters, quote and
backslash use precisely the escapes in RFC 8785 section 3.2.2.2; slash is literal.
Non-ASCII scalars are emitted directly. Numbers use the ECMAScript-compatible
shortest binary64 representation required by RFC 8785 section 3.2.2.3.

The entire Package contributes, including identity and optional fields. A typed
model MUST NOT silently drop a field before hashing or accepting custody. An
implementation unable to represent an envelope must refuse it, not hash a
projection. This does not finish the separate Package schema binding (D-003).

## One digest, wherever custody uses it

Let C be these canonical bytes. `SHA-256(C)` MUST be the same digest used for
possession, AC, exact replay and returned acceptance validation. The textual
form remains `sha256:` plus lowercase hex. PACKAGE-POSSESSION-1's HMAC rule is
unchanged. Byte counts for Introduction limits count C.

Protected native JSON must use the same strict input rules. Invalid input must
be rejected before Package admission. Merely parsing a vector through a separate
test-only decoder does not establish ingress conformance.

## Historical facts and implementation scope

This amendment changes bytes for some previously accepted values. It MUST NOT
be deployed as an implicit rehash of existing LG/AC/CL or a fallback that tries
two digests. This experiment runs fresh stores only; existing repository facts
and evidence remain immutable. Negotiation and migration of histories produced
before the binding are not solved here. Both implementations must conform to
one binding in the experiment; neither chooses a peer-specific serializer.

The production Package digest/proof and protected-carriage paths are in scope.
Other authority protocols and old file readers are not automatically claimed to
conform merely because this codec exists. Verification records the paths tested.
